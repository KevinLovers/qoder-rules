# MFQ 文本测试用例生成策略检查快速使用指南

## 📋 概述

本指南帮助您快速了解和使用 MFQ 文本测试用例生成策略检查，确保生成的文本格式测试用例符合 M（单功能）、F（组合）、Q（非功能）测试点生成策略要求。

## 🚀 快速开始

### 1. 启用文本测试用例检查策略

在 AI 对话中引用规范文件：

```
@quality/MFQ-text-test-case-spec.zh-CN.md

请为以下功能生成文本格式的测试用例：
- 用户登录功能
- 输入：用户名、密码
- 验证：登录成功/失败
```

### 2. 配置检查策略

#### 方式一：使用配置文件（推荐）

```bash
# 复制配置文件模板
cp .mfq-text-test-case-check.yaml.example .mfq-text-test-case-check.yaml

# 编辑配置文件
vim .mfq-text-test-case-check.yaml
```

#### 方式二：在文本中指定

```
【测试用例标识】M-001
【测试用例类型】单功能测试（M）- 正向测试
【优先级】高
【标签】smoke、login
```

## 📝 10个检查项详解

### [检查 1] 格式完整性

**检查内容**：
- ✅ 包含测试用例标识（M-001, F-001, Q-001）
- ✅ 包含测试用例名称和描述
- ✅ 包含测试步骤和预期结果
- ✅ 使用结构化格式

**示例**：
```
【测试用例标识】M-001
【测试用例名称】用户使用有效凭据登录应成功
【测试用例类型】单功能测试（M）- 正向测试
【测试目标】验证用户使用有效的用户名和密码能够成功登录系统

【前置条件】
1. 系统已部署并正常运行
2. 存在有效的测试用户账号

【测试步骤】
1. 打开登录页面
2. 输入有效用户名：testuser@example.com
3. 输入有效密码：TestPass123!
4. 点击登录按钮

【预期结果】
1. 页面成功跳转到首页
2. 显示欢迎信息："欢迎, testuser@example.com"
```

### [检查 2] M-单功能测试用例

**检查内容**：
- ✅ 测试用例标识以"M-"开头
- ✅ 包含正向、边界、异常三类测试用例
- ✅ 每个功能至少3-5个M测试用例

**示例**：
```
【测试用例标识】M-001
【测试用例名称】用户使用有效凭据登录应成功
【测试用例类型】单功能测试（M）- 正向测试

【测试用例标识】M-002
【测试用例名称】用户名为空时登录应显示错误提示
【测试用例类型】单功能测试（M）- 边界测试

【测试用例标识】M-003
【测试用例名称】用户使用无效密码登录应失败
【测试用例类型】单功能测试（M）- 异常测试
```

### [检查 3] F-组合交叉测试用例

**检查内容**：
- ✅ 测试用例标识以"F-"开头
- ✅ 涉及多个参数或功能组合
- ✅ 使用配对测试或正交表方法
- ✅ 测试用例数量少于全组合的50-80%

**示例**：
```
【测试用例标识】F-001
【测试用例名称】用户名和密码组合验证 - 有效用户名+有效密码
【测试用例类型】组合测试（F）- 配对测试
【测试方法】使用配对测试生成测试用例

【测试数据】
- 用户名：有效（testuser@example.com）
- 密码：有效（TestPass123!）

【测试用例标识】F-002
【测试用例名称】用户名和密码组合验证 - 有效用户名+无效密码
【测试用例类型】组合测试（F）- 配对测试
```

### [检查 4] Q-非功能测试用例

**检查内容**：
- ✅ 测试用例标识以"Q-"开头
- ✅ 包含性能、安全、并发等测试用例
- ✅ 性能指标可量化
- ✅ 安全测试覆盖OWASP Top 10

**示例**：
```
【测试用例标识】Q-001
【测试用例名称】登录接口响应时间应小于100毫秒
【测试用例类型】非功能测试（Q）- 性能测试
【性能指标】
- 响应时间阈值：100毫秒
- 测试数据量：1000次请求

【测试用例标识】Q-002
【测试用例名称】SQL注入攻击应被阻止
【测试用例类型】非功能测试（Q）- 安全测试
【安全测试类型】OWASP Top 10 - SQL注入
```

### [检查 5] 命名规范

**检查内容**：
- ✅ 测试用例标识格式：{类型}-{序号}
- ✅ 类型标识：M（单功能）、F（组合）、Q（非功能）
- ✅ 序号：3位数字（001, 002, 003...）
- ✅ 测试用例名称清晰描述预期行为

**示例**：
```
✅ 正确：
M-001: 用户使用有效凭据登录应成功
F-001: 用户名和密码组合验证应覆盖所有边界情况
Q-001: 登录接口响应时间应小于100毫秒

❌ 错误：
测试1
登录测试
M1: 测试    # 序号格式错误
```

### [检查 6] 内容完整性

**检查内容**：
- ✅ 测试步骤清晰、可操作
- ✅ 预期结果明确、可验证
- ✅ 测试数据完整

**示例**：
```
✅ 正确：
【测试步骤】
1. 打开浏览器，访问 https://example.com/login
2. 在"用户名"输入框中输入：testuser@example.com
3. 在"密码"输入框中输入：TestPass123!
4. 点击"登录"按钮

【预期结果】
1. 页面成功跳转到首页（URL: https://example.com/home）
2. 页面顶部显示欢迎信息："欢迎, testuser@example.com"
```

### [检查 7] 独立性

**检查内容**：
- ✅ 每个测试用例包含完整的前置条件
- ✅ 测试用例不依赖其他测试用例的执行结果
- ✅ 测试用例可以单独执行

### [检查 8] 分类和标签

**检查内容**：
- ✅ 测试用例类型正确标识（M/F/Q）
- ✅ 包含优先级和标签（建议）

**示例**：
```
【测试用例标识】M-001
【测试用例类型】单功能测试（M）- 正向测试
【优先级】高
【标签】smoke、login、positive
```

### [检查 9] 覆盖度

**检查内容**：
- ✅ M测试用例覆盖正向、边界、异常三类
- ✅ F测试用例覆盖关键参数组合
- ✅ Q测试用例覆盖性能、安全、并发等维度

### [检查 10] 可读性和可维护性

**检查内容**：
- ✅ 使用清晰的结构化格式
- ✅ 使用业务语言，避免技术黑话
- ✅ 包含必要的注释和说明

## ⚙️ 检查策略配置

### 检查模式

#### 严格模式（Strict Mode）
```yaml
check_mode: "strict"
# 所有检查项必须通过，否则测试用例生成失败
```

#### 宽松模式（Lenient Mode）
```yaml
check_mode: "lenient"
warn_threshold: 3
# 检查项失败时发出警告，但不阻止测试用例生成
```

### 配置示例

```yaml
mfq_text_test_case:
  check_mode: "strict"
  
  # M测试用例检查
  monolithic_tests:
    min_test_cases: 3
    require_positive: true
    require_boundary: true
    require_negative: true
  
  # F测试用例检查
  combination_tests:
    combination_method: "pairwise"
    max_reduction_rate: 70
  
  # Q测试用例检查
  quality_tests:
    require_performance: true
    require_security: true
```

```
- 用户登录功能
```

```
@quality/MFQ-text-test-case-spec.zh-CN.md

POST /api/users/login
Body: { username, password }
Response: { token, user_id }
```

**AI 将生成**：
- ✅ M测试用例：单个参数验证
- ✅ F测试用例：参数组合验证


## 📚 最佳实践

1. **使用结构化格式**：使用明确的格式标记（【测试用例标识】、【测试步骤】等）
2. **包含M测试用例**：所有功能都应该有M测试用例
3. **使用业务语言**：避免技术黑话，使用清晰的业务语言
4. **保持测试独立**：每个测试用例应该独立运行
5. **包含错误处理**：测试错误情况和边界条件
6. **量化性能指标**：Q测试用例的性能指标应该可量化
7. **遵循命名规范**：使用清晰的测试用例描述

## ❓ 常见问题

### Q1: 检查失败怎么办？

**A**: 根据检查报告修复问题：
- 关键检查项失败：必须修复
- 重要检查项失败：建议修复
- 一般检查项失败：可选修复

### Q2: 如何跳过某些检查项？

**A**: 在配置文件中禁用：
```yaml
mfq_text_test_case:
  classification:
    enabled: false  # 禁用分类和标签检查
```

### Q3: 测试用例必须包含F和Q测试用例吗？

**A**: 根据项目需求：
- M测试用例：必须包含
- F测试用例：多参数组合时建议包含
- Q测试用例：关键功能建议包含

### Q4: 如何自定义格式标记？

**A**: 在配置文件中修改：
```yaml
mfq_text_test_case:
  format:
    format_markers:
      - "【测试用例标识】"
      - "【测试用例名称】"
      - "【测试步骤】"
      - "【预期结果】"
```
