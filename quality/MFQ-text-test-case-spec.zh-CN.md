# 2. 根据项目需求启用/禁用规则

## [检查 1] 文本测试用例格式完整性 [ENABLED]
# 确保文本测试用例包含必要的格式元素

STATUS: ENABLED
说明：
- 文本测试用例必须包含完整的格式结构
- 必须包含测试用例标识、描述、前置条件、测试步骤、预期结果等
- 格式必须清晰、结构化、易于理解

检查项：
- ✅ 包含测试用例标识（M-001, F-001, Q-001）
- ✅ 包含测试用例标题/名称
- ✅ 包含测试用例描述
- ✅ 包含前置条件（如适用）
- ✅ 包含测试步骤
- ✅ 包含预期结果
- ✅ 包含测试数据（如适用）
- ✅ 格式清晰，使用结构化标记

示例：
```
【测试用例标识】M-001
【测试用例名称】用户使用有效凭据登录应成功
【测试用例类型】单功能测试（M）
【优先级】高
【测试目标】验证用户使用有效的用户名和密码能够成功登录系统

【前置条件】
1. 系统已部署并正常运行
2. 存在有效的测试用户账号
3. 用户已打开登录页面

【测试数据】
- 用户名：testuser@example.com
- 密码：TestPass123!

【测试步骤】
1. 打开登录页面
2. 在用户名输入框中输入：testuser@example.com
3. 在密码输入框中输入：TestPass123!
4. 点击"登录"按钮
5. 等待页面跳转

【预期结果】
1. 页面成功跳转到首页
2. 页面显示欢迎信息："欢迎, testuser@example.com"
3. 用户状态显示为"已登录"
4. 浏览器地址栏显示首页URL

【后置条件】
- 用户已成功登录系统
- 可以执行后续操作

【备注】
- 此测试用例属于正向测试
- 验证正常业务流程
```

# ❌ 错误：格式不完整，缺少必要元素
测试登录功能
输入用户名和密码
点击登录按钮
应该成功
```

检查策略：
- ✅ 必须包含测试用例标识（M/F/Q-序号）
- ✅ 必须包含测试用例名称和描述
- ✅ 必须包含测试步骤和预期结果
- ✅ 格式必须结构化，使用明确的标记


## [检查 2] M-单功能测试用例检查 [ENABLED]
# 确保M测试用例符合单功能测试要求

STATUS: ENABLED
说明：
- M测试用例必须针对单个功能进行测试
- 必须包含正向、边界、异常三类测试用例
- 每个功能至少生成3-5个M测试用例

检查项：
- ✅ 测试用例标识以"M-"开头
- ✅ 测试用例针对单个功能
- ✅ 包含正向测试用例（正常输入，预期正确输出）
- ✅ 包含边界测试用例（边界值输入）
- ✅ 包含异常测试用例（无效输入，验证错误处理）
- ✅ 每个功能至少3-5个M测试用例
- ✅ 测试用例独立，不依赖其他测试用例

示例：
```
【测试用例标识】M-001
【测试用例名称】用户使用有效凭据登录应成功
【测试用例类型】单功能测试（M）- 正向测试
【测试目标】验证用户使用有效的用户名和密码能够成功登录

【测试步骤】
1. 打开登录页面
2. 输入有效用户名：testuser@example.com
3. 输入有效密码：TestPass123!
4. 点击登录按钮

【预期结果】
- 登录成功
- 跳转到首页
- 显示欢迎信息

---

【测试用例标识】M-002
【测试用例名称】用户名为空时登录应显示错误提示
【测试用例类型】单功能测试（M）- 边界测试
【测试目标】验证用户名为空时的错误处理

【测试步骤】
1. 打开登录页面
2. 用户名输入框留空
3. 输入有效密码：TestPass123!
4. 点击登录按钮

【预期结果】
- 显示错误提示："用户名不能为空"
- 页面不跳转
- 仍在登录页面

---

【测试用例标识】M-003
【测试用例名称】用户使用无效密码登录应失败
【测试用例类型】单功能测试（M）- 异常测试
【测试目标】验证使用无效密码时的错误处理

【测试步骤】
1. 打开登录页面
2. 输入有效用户名：testuser@example.com
3. 输入无效密码：wrongpassword
4. 点击登录按钮

【预期结果】
- 显示错误提示："用户名或密码错误"
- 页面不跳转
- 仍在登录页面
```

检查策略：
- ✅ M测试用例必须包含正向、边界、异常三类
- ✅ 每个功能至少3个M测试用例
- ✅ 测试用例标识格式：M-{序号}
- ✅ 测试用例必须独立


## [检查 3] F-组合交叉测试用例检查 [ENABLED]
# 确保F测试用例符合组合交叉测试要求

STATUS: ENABLED
说明：
- F测试用例必须测试多个功能组合或参数交叉的情况
- 使用正交表或配对测试方法生成
- 测试用例数量应少于全组合数量（通常减少50-80%）

检查项：
- ✅ 测试用例标识以"F-"开头
- ✅ 测试用例涉及多个参数或功能组合
- ✅ 使用配对测试或正交表方法生成
- ✅ 测试用例数量少于全组合数量
- ✅ 关键参数组合被覆盖
- ✅ 记录使用的组合测试方法

示例：
```
【测试用例标识】F-001
【测试用例名称】用户名和密码组合验证 - 有效用户名+有效密码
【测试用例类型】组合测试（F）- 配对测试
【测试目标】验证用户名和密码的有效组合

【测试数据】
- 用户名：有效（testuser@example.com）
- 密码：有效（TestPass123!）

【测试步骤】
1. 打开登录页面
2. 输入有效用户名
3. 输入有效密码
4. 点击登录按钮

【预期结果】
- 登录成功

---

【测试用例标识】F-002
【测试用例名称】用户名和密码组合验证 - 有效用户名+无效密码
【测试用例类型】组合测试（F）- 配对测试
【测试目标】验证用户名和密码的无效组合

【测试数据】
- 用户名：有效（testuser@example.com）
- 密码：无效（wrongpassword）

【测试步骤】
1. 打开登录页面
2. 输入有效用户名
3. 输入无效密码
4. 点击登录按钮

【预期结果】
- 登录失败
- 显示错误提示

---

【测试用例标识】F-003
【测试用例名称】用户名、密码、验证码组合验证
【测试用例类型】组合测试（F）- 正交表测试
【测试方法】使用L9(3^4)正交表生成9个测试用例

【测试数据组合】
组合1：用户名(有效) + 密码(有效) + 验证码(有效)
组合2：用户名(有效) + 密码(无效) + 验证码(无效)
组合3：用户名(无效) + 密码(有效) + 验证码(无效)

3. 输入对应的密码
4. 输入对应的验证码

【预期结果】
根据组合的有效性，预期登录成功或失败
```

- ✅ F测试用例必须使用组合测试方法
- ✅ 测试用例数量应少于全组合的50-80%
- ✅ 必须记录使用的组合测试方法
- ✅ 关键参数组合必须被覆盖


## [检查 4] Q-非功能测试用例检查 [ENABLED]
# 确保Q测试用例符合非功能测试要求

STATUS: ENABLED
说明：
- Q测试用例必须针对非功能需求进行测试
- 包括性能、安全、并发、压力等测试类型
- 每个非功能维度至少生成2-3个测试用例

检查项：
- ✅ 测试用例标识以"Q-"开头
- ✅ 测试用例针对非功能需求
- ✅ 包含性能测试用例（响应时间、吞吐量等）
- ✅ 包含安全测试用例（认证、授权、注入攻击等）
- ✅ 包含并发测试用例（多用户并发、竞态条件等）
- ✅ 包含压力测试用例（极限负载、资源耗尽等）
- ✅ 性能指标可量化
- ✅ 安全测试覆盖OWASP Top 10

示例：
```
【测试用例标识】Q-001
【测试用例名称】登录接口响应时间应小于100毫秒
【测试用例类型】非功能测试（Q）- 性能测试
【测试目标】验证登录接口的响应时间符合性能要求

【性能指标】
- 响应时间阈值：100毫秒
- 测试环境：生产环境
- 测试数据量：1000次请求

【测试步骤】
1. 准备1000个有效用户账号
2. 使用性能测试工具（如JMeter）发送登录请求
3. 记录每次请求的响应时间
4. 统计平均响应时间、最大响应时间、最小响应时间

【预期结果】
- 平均响应时间 < 100毫秒
- 95%的请求响应时间 < 100毫秒
- 最大响应时间 < 200毫秒

---

【测试用例标识】Q-002
【测试用例名称】SQL注入攻击应被阻止
【测试用例名称】非功能测试（Q）- 安全测试
【测试目标】验证系统能够防止SQL注入攻击

【安全测试类型】OWASP Top 10 - SQL注入

【测试数据】
- 恶意输入：'; DROP TABLE users; --
- 测试位置：用户名输入框

【测试步骤】
1. 打开登录页面
2. 在用户名输入框中输入：'; DROP TABLE users; --
3. 输入任意密码
4. 点击登录按钮
5. 检查数据库状态

【预期结果】
- 系统拒绝恶意输入
- 显示错误提示（不暴露数据库错误信息）
- 数据库users表未被删除
- 系统日志记录安全事件

---

【测试用例标识】Q-003
【测试用例名称】100个并发用户登录应全部成功
【测试用例类型】非功能测试（Q）- 并发测试
【测试目标】验证系统能够处理并发登录请求

【并发指标】
- 并发用户数：100
- 测试持续时间：60秒
- 每个用户执行登录操作

【测试步骤】
1. 准备100个有效用户账号
2. 使用并发测试工具同时发送100个登录请求
3. 监控系统资源使用情况（CPU、内存、数据库连接）
4. 记录每个请求的成功/失败状态

【预期结果】
- 100个并发请求全部成功
- 系统资源使用正常（CPU < 80%, 内存 < 80%）
- 数据库连接数在合理范围内
- 无数据竞争或死锁现象
```

检查策略：
- ✅ Q测试用例必须包含性能、安全、并发等维度
- ✅ 每个非功能维度至少2-3个测试用例
- ✅ 性能指标必须可量化
- ✅ 安全测试必须覆盖OWASP Top 10

- ✅ 测试用例不依赖其他测试用例的执行结果
- ✅ 测试用例可以单独执行
- ✅ 测试用例执行顺序不影响结果

```

## 检查策略配置文件

检查策略可以通过配置文件进行设置：

```yaml
# .mfq-text-test-case-check.yaml
mfq_text_test_case:
  # 检查模式：strict（严格模式）或 lenient（宽松模式）
  check_mode: "strict"
  warn_threshold: 3

  # [检查 1] 格式完整性检查
  format:
    enabled: true
    require_test_case_id: true          # 必须包含测试用例标识
    require_test_case_name: true        # 必须包含测试用例名称
    require_description: true           # 必须包含描述
    require_test_steps: true            # 必须包含测试步骤
    require_expected_result: true      # 必须包含预期结果
    require_structured_format: true     # 必须使用结构化格式

  # [检查 2] M-单功能测试用例检查
  monolithic_tests:
    enabled: true
    require_m_prefix: true               # 必须包含M-前缀
    min_test_cases: 3                   # 每个功能最少测试用例数
    require_positive: true               # 必须包含正向测试用例
    require_boundary: true               # 必须包含边界测试用例
    require_negative: true               # 必须包含异常测试用例
    require_independence: true           # 测试用例必须独立

  # [检查 3] F-组合交叉测试用例检查
  combination_tests:
    enabled: true
    require_f_prefix: true               # 必须包含F-前缀
    require_combination_method: true     # 必须记录组合测试方法
    require_key_combinations: true       # 必须包含关键组合
    max_reduction_rate: 80               # 最多减少80%的测试用例

  # [检查 4] Q-非功能测试用例检查
  quality_tests:
    enabled: true
    require_q_prefix: true               # 必须包含Q-前缀
    require_performance: true             # 必须包含性能测试用例
    require_security: true                # 必须包含安全测试用例
    require_concurrency: false            # 是否必须包含并发测试用例（可选）
    require_quantifiable_metrics: true    # 性能指标必须可量化
    require_owasp_top10: true             # 安全测试必须覆盖OWASP Top 10

  # [检查 5] 命名规范检查
  naming:
    enabled: true
    require_mfq_prefix: true              # 必须包含MFQ前缀
    pattern: "{type}-{seq:03d}: {description}"
    types: ["M", "F", "Q"]
    min_name_length: 10
    max_name_length: 100
    require_business_language: true       # 必须使用业务语言

  # [检查 6] 内容完整性检查
  content:
    enabled: true
    require_clear_steps: true             # 测试步骤必须清晰
    require_verifiable_results: true     # 预期结果必须可验证
    require_complete_data: true           # 测试数据必须完整

  # [检查 7] 独立性检查
  independence:
    enabled: true
    require_complete_prerequisites: true  # 前置条件必须完整
    require_independent_execution: true  # 必须可以独立执行
    forbid_dependencies: true             # 禁止测试用例之间的依赖

  # [检查 8] 分类和标签检查
  classification:
    enabled: true
    require_type_identification: true    # 必须标识测试用例类型
    require_priority: false               # 是否必须包含优先级（建议）
    require_tags: false                   # 是否必须包含标签（建议）

  # [检查 9] 覆盖度检查
  coverage:
    enabled: true
    require_m_coverage: true              # M测试用例必须覆盖三类情况
    require_f_coverage: true              # F测试用例必须覆盖关键组合
    require_q_coverage: true              # Q测试用例必须覆盖主要维度
    min_m_per_function: 3                # 每个功能最少M测试用例数

  # [检查 10] 可读性和可维护性检查
  maintainability:
    enabled: true
    require_structured_format: true      # 必须使用结构化格式
    require_business_language: true      # 必须使用业务语言
    require_clear_descriptions: true     # 描述必须清晰
```

## 检查项优先级

### 关键检查项（必须通过）
- 格式完整性（测试用例标识、名称、步骤、预期结果）

- 内容完整性（步骤清晰、结果可验证）
- 独立性（测试用例独立）

### 重要检查项（建议通过）
- F测试用例要求（F-前缀、组合方法）
- Q测试用例要求（Q-前缀、性能/安全覆盖）
- 覆盖度要求（三类覆盖、关键组合）
- 分类和标签（类型标识、优先级）

### 一般检查项（可选）
- 可读性和可维护性（格式、语言）
- 标签使用（smoke、regression等）
